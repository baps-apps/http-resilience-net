# Using HttpResilience.NET 1.0.0

**This document describes version 1.0.0 only, and is frozen.** Every other document in this repository
describes 2.0.0, whose API and configuration schema are different. Nothing here forward-references 2.0.0;
nothing elsewhere applies here.

1.0.0 configures [`Microsoft.Extensions.Http.Resilience`](https://learn.microsoft.com/dotnet/core/resilience/http-resilience)
and Polly from a single configuration section: retry, circuit breaker, timeouts, and optional rate limiting,
bulkhead, fallback and hedging.

## Registration

Two calls. The options registration comes first, and both take the **same** `IConfiguration` instance.

```csharp
using Microsoft.Extensions.DependencyInjection;

builder.Services.AddHttpResilienceOptions(builder.Configuration);

builder.Services.AddHttpClient("Orders", c => c.BaseAddress = new Uri("https://orders.internal"))
    .AddHttpClientWithResilience(builder.Configuration);
```

`AddHttpClientWithResilience` reads `HttpResilienceOptions.Enabled`. When it is `false` or absent the builder
is returned unchanged and no resilience is applied — nothing is logged.

### Public API

| Member | Purpose |
| --- | --- |
| `services.AddHttpResilienceOptions(IConfiguration)` | Binds and validates the `HttpResilienceOptions` section. |
| `services.AddHttpResilienceOptions(IConfigurationSection)` | Same, from a section you name — used for per-client sections. |
| `builder.AddHttpClientWithResilience(IConfiguration, int? requestTimeoutSeconds = null)` | Applies the pipeline to one client. |
| `builder.AddHttpClientWithResilience(IConfigurationSection, int? requestTimeoutSeconds = null)` | Same, from a named section. |
| `builder.AddHttpClientWithResilience(IConfiguration, int?, IHttpFallbackHandler?)` | Same, with a custom fallback handler. |
| `builder.AddHttpClientWithResilience(..., Action<IHttpClientBuilder>? configurePipeline)` | Adds your own handlers outside the built-in ones. |
| `builder.AddHttpClientWithResilience(..., Action<ResiliencePipelineBuilder<HttpResponseMessage>> configureInnerPipeline, ...)` | Replaces the inner pipeline entirely. **Ignores its `fallbackHandler` argument and skips validation** — see [Known defects](#known-defects-in-100). |
| `services.AddHttpResilienceHealthChecks(string name = "http-resilience", HealthStatus? failureStatus = null, IEnumerable<string>? tags = null)` | Circuit-breaker state as a health check. |
| `services.AddHttpResilienceTelemetry()` | Adds the `error.type` tag to Polly metering events. |
| `HttpResilienceTelemetryExtensions.PollyMeterName` | `"Polly"` — the meter name to hand an OpenTelemetry SDK. |

## Per-client configuration

1.0.0 has no inheritance model. Each client points at a whole section, and every section is independent —
a section states its full configuration or takes the property defaults.

```json
{
  "HttpResilienceOptions": {
    "Enabled": true,
    "PipelineOrder": [ "Standard" ],
    "Timeout": { "TotalRequestTimeoutSeconds": 30, "AttemptTimeoutSeconds": 10 }
  },

  "HttpResilienceOptions:Reports": {
    "Enabled": true,
    "PipelineOrder": [ "Standard" ],
    "Timeout": { "TotalRequestTimeoutSeconds": 120, "AttemptTimeoutSeconds": 30 }
  }
}
```

```csharp
builder.Services.AddHttpClient("Reports")
    .AddHttpClientWithResilience(builder.Configuration.GetSection("HttpResilienceOptions:Reports"));
```

`requestTimeoutSeconds` overrides `Timeout:TotalRequestTimeoutSeconds` for one client in code, which is the
only override that does not need a section of its own.

## Choosing the pipeline

`PipelineOrder` is a list of strategy names. Valid entries: `Fallback`, `Bulkhead`, `RateLimiter`,
`Standard`, `Hedging`. `Standard` is retry + circuit breaker + timeouts; `Hedging` races concurrent attempts
and takes the first success. The two are alternatives — list one or the other, not both.

```json
{ "PipelineOrder": [ "Bulkhead", "RateLimiter", "Standard" ] }
```

> **Read [Known defects](#known-defects-in-100) before relying on a multi-strategy `PipelineOrder`.**

## Fallback

With `Fallback:Enabled`, a failed call returns a synthetic response built from `StatusCode` and
`ResponseBody` instead of throwing. Supply `IHttpFallbackHandler` to compute one instead; returning `null`
falls through to the synthetic response.

```csharp
public sealed class OrdersFallback : IHttpFallbackHandler
{
    public ValueTask<HttpResponseMessage?> TryHandleAsync(
        HttpFallbackContext context, CancellationToken cancellationToken)
    {
        if (context.Exception is not null)
        {
            return ValueTask.FromResult<HttpResponseMessage?>(null);
        }

        return ValueTask.FromResult<HttpResponseMessage?>(
            new HttpResponseMessage(HttpStatusCode.OK) { Content = new StringContent("[]") });
    }
}

builder.Services.AddHttpClient("Orders")
    .AddHttpClientWithResilience(builder.Configuration, new OrdersFallback());
```

A fallback converts a failure into a success from the caller's point of view. Do not enable it on a client
whose caller needs to know the call failed.

## Health checks and telemetry

```csharp
builder.Services.AddHttpResilienceHealthChecks(tags: [ "dependency" ]);
builder.Services.AddHttpResilienceTelemetry();

builder.Services.AddOpenTelemetry().WithMetrics(m => m
    .AddMeter(HttpResilienceTelemetryExtensions.PollyMeterName)   // "Polly"
    .AddHttpClientInstrumentation()
    .AddOtlpExporter());
```

The check itself returns `Healthy` when every breaker is closed and `Degraded` when any is open or half-open,
regardless of `failureStatus` — that parameter is only consulted if the check *throws*, where it defaults to
`Unhealthy`. Since ASP.NET Core maps Degraded to HTTP 200 by default, the endpoint's status code carries no
signal on its own. Do not gate a liveness or readiness probe on it: an open circuit means a *downstream* is
unhealthy, and restarting the pod sheds capacity during a dependency outage.

1.0.0 publishes no meter of its own. `"Polly"` is the only meter name to register, and it covers every Polly
pipeline in the process.

## Known defects in 1.0.0

These are behaviors of the shipped 1.0.0 package. They are listed so a service running it can work around
them.

- **Every HTTP method is retried, POST included.** Nothing in 1.0.0 filters by method — neither an allow-list
  nor the platform's `DisableForUnsafeHttpMethods` — so a transient failure on a POST, PUT, PATCH, DELETE or
  any custom method re-sends the same body to the origin up to `MaxRetryAttempts` more times. This is the
  most consequential item on this list. Give clients that send mutating requests a section of their own with
  `Retry: { "MaxRetryAttempts": 0 }` unless the endpoint deduplicates on an idempotency key.
- **`PipelineOrder` is applied in reverse.** Handlers are added by iterating the list from the last entry to
  the first, and `IHttpClientFactory` treats the first handler added as the outermost, so
  `[ "Bulkhead", "RateLimiter", "Standard" ]` composes as `Standard → RateLimiter → Bulkhead`: the limiters
  sit *inside* the retry loop, and each retry consumes its own permit and slot. A single-entry
  `PipelineOrder` is unaffected. Use one entry unless you have verified the resulting order against origin
  call counts.
- **Hedging repeats mutating methods too**, and hedged attempts arrive *simultaneously*, so an origin's
  idempotency key has no serialization to rely on. Only put `Hedging` in `PipelineOrder` for clients that
  send safe methods.
- **The overload taking `Action<ResiliencePipelineBuilder<HttpResponseMessage>>` accepts an
  `IHttpFallbackHandler` and never wires it.** The parameter binds and is silently ignored. That overload
  also bypasses the options validator. Prefer the section-based overloads.
- **Nothing prevents a second registration on one client.** Calling `AddHttpClientWithResilience` twice on
  the same builder nests two pipelines, and nested pipelines multiply retries rather than adding them.
- **`Connection:Enabled` applies settings through `ConfigurePrimaryHttpMessageHandler`, which is last-wins.**
  Any later `ConfigurePrimaryHttpMessageHandler` on the same client — a client certificate, a proxy, a test
  stub — replaces the configured handler and every connection setting with it, silently. Register connection
  settings last, or leave `Connection:Enabled` at `false` and configure your own `SocketsHttpHandler`.
- **`HttpClient.Timeout` is left at the infinite value `AddStandardResilienceHandler` sets.** Pipeline
  timeouts stop applying at response headers, so a response body that stalls afterwards is bounded by
  nothing. Set a finite `HttpClient.Timeout` through `ConfigureHttpClient`, or read with
  `HttpCompletionOption.ResponseHeadersRead` and impose your own deadline on the stream.
- **Metric dimensions are unbounded under `PipelineSelection:Mode: ByAuthority` and under `Hedging`.** Both
  mint a pipeline, a circuit breaker and a metric series per request authority, with no allow-list and
  nothing to evict them. Do not use either on a client whose destination comes from request data.
- **The rate limiter is process-local**, so the fleet-wide rate is `replicas × PermitLimit` per window. It
  cannot enforce a cluster-wide quota.
